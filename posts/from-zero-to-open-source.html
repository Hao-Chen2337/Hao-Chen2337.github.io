从零开始参与开源

2026-09-12 约 1700 字 # 开源 # 甲辰计划 # RISC-V # LLVM

放暑假之前，吴伟老师来学校宣讲了甲辰计划，也讲了讲开源生态。

现今 AI 发展得很快，但对普通学生来说又是另一回事：招聘看重"相关项目经历"，可实习又往往要求你有实习经历——多少有点鸡生蛋、蛋生鸡。这道门槛本来就不好过，如今只会更高。学校里教的东西和企业实际在用的，也隔着一条看不见的河。

甲辰计划提供的，正好是这样一个真正参与进去的平台——不要求你带着项目经历进来，而是给你一个从零开始接触真实项目的机会。

入坑

我参加的是线上实习。吴老师推荐了一些方向，我对 AI 软件栈比较感兴趣。他建议先学 MIT 的《计算机教育中缺失的一课》和几门基础课。虽然没有学得多深入，但确实补上了一些后面开发需要的基本工具。

一两周后，吴老师建议先别急着写代码，先看看 K3 的芯片技术手册，再看看 llama.cpp 里 RISC-V 向量（RVV）相关的前人 PR。

项目很大，我也没指望一开始就看懂，于是从最简单的地方入手：读代码、部署、把测试跑通。部署的过程一路撞墙，却也让我第一次意识到，"编译"本身就有不少东西要学。

从 QEMU 到真机

跑起来之后，我先测了一些正确性，接着想测性能，就在 QEMU 上试了试。它能告诉我结果对不对，却测不出到底有多快——我缺一个真实的硬件。

我去找吴老师申请，他把我拉进 SpaceMiT 社区群，让我自己去说。后来社区给了我一个 K3 云实例，一个可以 SSH 上去的远程环境。

深坑：TCM

有了真机之后，能测的东西一下多了，但也撞上了一个很深的坑：TCM。它是一块紧耦合内存，AI 核会大量使用，跑测试时线程数开大一点，程序就直接 abort。

我先用环境变量 SPACEMIT_DISABLE_TCM=1 绕过去，但绕过终究只是绕过。后来翻文档才发现，里面写得很清楚：反复崩溃后，这块内存不会自动释放，之后所有任务都会卡死，用 spacemit-tcm-smi 清一遍就好了。

我怀疑了一圈硬件，答案其实一直躺在文档里。

第一个 bug：缺了一行的派发表

有了真机，我做的第一件事就是把各种量化格式的模型挨个跑一遍，看看基准数据。

跑到 Q4_K_M 时，它慢得有些反常。我以为这里有性能问题，就开始查。查了半天没找到原因，倒是顺手拿它跑了一次对话——输出是乱码。

乱码一出来，性质就变了：慢可能是优化空间，乱码基本就是 bug。

顺着链路排查，最终定位到 SpaceMiT 后端的派发表：其余量化类型都有分支，唯独缺了 GGML_TYPE_Q5_0。Q4_K_M 属于混合量化格式，内部刚好包含 Q5_0 分片，所以触发了缺失分支。

case GGML_TYPE_Q5_0:

最意外的是，这个格式后面的计算逻辑其实已经写好了，只差这一句把它接上。

补上，重编，再跑——不乱码了，速度也正常了。两个 switch 各补一行，提了 PR，几天后被合并进上游。

给 clangd 修 bug

跑了一段时间后，我开始想动它的源码。我在 VS Code 里装了 clangd，但看某个文件时，扩展在后台反复退出：

The Clang Language Server server crashed 5 times in the last 3 minutes.
The server will not be restarted.

一开始我以为是自己的配置出了问题。后来重启、换文件，发现只有这个文件会崩，基本排除了配置问题，开始指向工具本身的 bug。把最新源码重新编了一遍，问题依旧。

于是把崩溃代码一点点删掉，最后缩到六行：

#include <map>
std::map<const Incomplete *, int> m;
struct Incomplete;
void f(Incomplete *p) { m[p]; }

一个只有前置声明、还没定义的类型被拿来当 map 的 key，再对它的指针做下标运算。clang-tidy 的检查直接去问它："你是多态的吗？"——可这个类型连定义都没有，这个问题本来就不该被问出来。

修复也很简单：判断之前先确认它有定义。

AST_MATCHER(CXXRecordDecl, isPolymorphic) {
  return Node.hasDefinition() && Node.isPolymorphic();
}

类似的地方有两处，都改掉了。LLVM 那边还要求补一个回归测试，我也一并加上了。

提上去之后就是等待和来回修改：评审说注释太多，我删了；文档要补，我补了。最后让我填 Release Note，CI 又报了个错——不过只是字母顺序。

收获

回头看，我最后交出去的其实只是两处很小的 bug 修复，但这段经历带给我的东西远不止代码本身。

做项目的过程里，我一直在读官方文档、翻上游源码、学习新工具，缺什么补什么。项目太大，根本读不完，也不存在真正"读懂了"的那一天。保持学习、慢慢沉淀，大概才是常态。现在 AI agent 也让查资料、读陌生代码方便了不少，但真正把问题解决掉，还是得自己理解。

另一个很深的体会是沟通与协作。很多资源不会自己送到面前。申请 K3 云实例是这样，提交 PR 后和维护者来回修改也是这样，都得主动开口，把问题说清楚。怎么协作、怎么把问题讲明白，课堂很少教，但实际工程里又缺不了。

也是在这个过程中，我第一次真正体会到开源精神。社区里很多维护者以志愿者的身份参与，把代码和技术开放出来，让后来的人能够站在前人的基础上继续走。

受这份精神感染，我也搭了个博客 imhaochen.com，把这次的测试数据整理公开。数据还有些偏差，也谈不上多严谨，但希望能给同方向的学习者一点参考。另外，我也试着写了些自用的小工具，现在大概只能服务自己，以后打磨好了，也许也能分享给社区。

我也明白，现阶段的我还改不动项目架构，只能从很小的补丁入手。但成长本来就是慢慢来的：先把小事做好，能力一点点攒起来，以后才有机会去碰更深、更复杂的东西。

写在最后

很感谢甲辰计划给我的机会，让我能真正踏进开源世界，亲眼看看一个庞大的社区是怎么运转的。

这段经历在我心里种下了一颗种子：不必等自己足够厉害才开始贡献，力所能及的分享和改进，本身就有价值。

往后，我会沿着底层技术这条路继续走，保持耐心，慢慢探索。
